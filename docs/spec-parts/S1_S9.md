## Handover notes

- **S3 (data model).** The `error` envelope is a five-field record with a fixed
  key order and `null`-preserving optionals; `context` is an untyped JSON value
  whose shape varies per code (the key sets are listed per row in S9.8). The
  `where` output is a five-field record with *omitted* optionals — the opposite
  optional policy from the error envelope. `--limit`/`--offset` are
  pointer-width unsigned; `--priority-min`/`--priority-max` are 8-bit unsigned;
  `--estimate` is signed 32-bit; `--lock-timeout` and `--activity-hours` are
  unsigned 64- and 32-bit.
- **S5 (outputs).** S9.30 quotes the empty-store bytes only as edge evidence;
  the general Plain and JSON layouts of `list`, `ready`, `blocked`, `stats`,
  `count`, `search`, `show`, `where` — including the glyph vocabulary
  (`✓ ○ ● ⊘ ✨ 📊`), the pagination envelope
  `{issues,total,limit,offset,has_more}`, the bare-array shape of `ready --json`
  and the two-space-indented pretty-printing used *only* by the error envelope —
  belong to S5. S5 also owns the observation that command results are compact
  JSON with one trailing LF while the error envelope is pretty-printed.
- **S6 (order).** Two order leaks surface through my sections: the
  ambiguous-id candidate list (hash-ordered in the original, canonicalized to
  byte order by DISC-005, S9.34) and the fixed declaration order of the
  subcommand list in `usage_none` and of the option lines in the `Options:`
  block (S1.16, S1.28). The `context` object's key order follows the literal
  construction order, not any sort.
- **S7 (numerics).** The argument-parse error texts expose the parsers:
  `invalid digit found in string` for the integer types and
  `<n> is not in 0..=255` for the 8-bit range check (S1.21, S1.22). `--limit +1`
  parses; `--limit -1` does not reach the parser at all. `0` is a sentinel
  meaning "unlimited" for `list --limit`, `ready --limit`, `blocked --limit` and
  `search --limit`, which S7 needs as a range note.
- **S8 (effects).** The error path performs exactly two effects: one write to
  stderr or stdout and one process exit with the code of S9.6. Environment
  reads are enumerated in S1.57–S1.67. `.beads/last-touched` is read by
  `show`/`update`/`close`/`reopen` when no id is given (S1.55). A run that
  reaches S9.14 has already written `issues.jsonl` and `last-touched` before it
  exits non-zero.
- **S10 (oddities).** Four candidates found here: (1) the usage line of
  `usage_unknown_flag` names the *suggested* option next to the already-consumed
  one (`Usage: br --no-db --no-auto-flush <COMMAND>`), and `--li` likewise
  produces `Usage: br list --limit <LIMIT>` (S1.15, S1.11); (2) the literal
  backticks around `SQLite`, `br close`, `dep add` and the like inside help and
  error text, which come from doc comments written for a lint (S1.28, S9.20,
  S9.21); (3) `INVALID_PRIORITY` duplicates its hint inside `context.hint`
  (S9.15); (4) the comma-splitting of label options is inconsistent across
  `create -l` (splits), `label add -l` (splits), `update --set-labels` (splits,
  by hand), `update --add-label` (does not), `list -l` (does not) — S1.33,
  S1.40, S1.52. Also: several codes that exist with an exit-5 or exit-6
  category are never reached, because the corresponding situation is a
  stdout no-op or is reported as a configuration error (S9.7, S9.28, S9.29).
- **S4 (algorithms).** The partial-id resolution rule that decides between
  `ISSUE_NOT_FOUND`, `AMBIGUOUS_ID` and a hit (S1.56) is an S4 algorithm; S9
  only records its three outcomes.
